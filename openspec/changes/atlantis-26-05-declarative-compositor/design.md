## Context

MR !28 (`feat/nixpkgs-26.05`) already carries most of this change: the 26.05
pins + regenerated lock, the 216-line `modules/home/hyprland.nix`, deletion
of `modules/nixos/wm/hyprland.nix` and the `.conf` chain, per-host monitor
and workspace attrs, `pathsToLink` on both hosts, and the gpg/ssh
matchBlocks migration. None of it has been built, booted, or verified. The
MR description documents only the two flake lines and claims the lock needs
regenerating (it does not — the branch's lock is already regenerated).
This change ratifies the existing branch shape, adds the missing
verification runbook, and makes the artifacts the review surface.

## Goals / Non-Goals

**Goals:**
- Both hosts verifiably building and running 26.05 (channel + lock + on-host
  proof), with stateVersion held at 25.11.
- Hyprland session config generated by home-manager (Lua), single source of
  truth, per-host topology via host attrs, `.conf` chain gone.
- MR !28's description rewritten to match the branch's real contents.
- A repeatable verification runbook: build → switch → reboot → re-switch →
  on-host channel proof → `.conf` purge check.

**Non-Goals:**
- Dendritic conversion of waybar/wofi/fastfetch/hyprpaper (follow-up change
  `atlantis-dendritic-layout`).
- Hyprland rice (animations, palette, bar replacement — later change).
- stateVersion bump (stays 25.11).
- MR !27 (blackhand nix-serve) — unrelated open MR, untouched.

## Decisions

- **Land on `feat/nixpkgs-26.05`, not a new branch.** The channel bump and
  compositor migration are one logical change already co-mingled on the
  branch (commit 8fe0c01e); the fold rule applies. The OpenSpec artifacts
  themselves live on a separate propose-only branch per the user's
  instruction.
- **NixOS-level `programs.hyprland` goes away entirely.** The old
  `modules/nixos/wm/hyprland.nix` is deleted rather than kept for
  `enable = true; xwayland` — home-manager's module owns the session now.
  The NixOS layer keeps only `display-manager.nix` and the `pathsToLink`
  portal wiring.
- **`.conf` purge is a documented manual step, not automation.**
  home-manager cannot delete orphan files; a one-time
  `rm -f ~/.config/hypr/hyprland.conf` on each host is recorded in tasks
  and the MR description, with the module comment explaining why.
- **Evaluation before verification.** `nixos-rebuild build` (or
  `nix flake check`) for both hosts precedes any switch; spider's import
  list already drops the deleted NixOS module on the branch — verify, don't
  assume.
- **Expected dbus-broker exit-4 on first switch.** A major-version jump may
  fail user-session activation with `Failed to reload user unit
  dbus-broker.service`. This is not a brick: reboot, then re-run switch to
  complete activation. Recorded in the runbook so it reads as expected
  behavior, not a failure.

## Risks / Trade-offs

- **Unverified branch is the baseline.** Everything on MR !28 is unaudited
  since Jul 31; the translation could carry subtle drops (verified: all 27
  workspace binds, both bindm, bezier, window_rule survived the move). The
  eval gate catches structural loss; visual/behavioral confirmation only
  happens at first login.
- **Multi-GiB closure swap on both hosts.** Blackhand just rebuilt on
  25.11; the 26.05 bump is another full closure download. Mitigation: MR !27
  (nix-serve on blackhand) would give spider a LAN substituter — but only if
  both hosts share the same lock, which they will once this merges.
- **Behavior drift inside the WM.** Hyprland 26.05's Lua migration may
  render some defaults differently (e.g. `no_hardware_cursors`). Binds and
  layout were translated faithfully; aesthetics were not tuned — that is
  explicitly the rice change's problem.
- **Two hosts, two maintenance windows.** Spider first (smaller, single
  head), blackhand second (triple-head, daily driver). A spider failure
  cheaply surfaces issues the blackhand window would hit expensively.
- **MR description rewrite churn.** Rewriting !28's description after 5+
  weeks open is bookkeeping noise, but the description currently lies about
  both the diff (two lines vs thirteen files) and buildability (lock already
  regenerated). Accurate documentation of a migration this size is worth
  the churn.
